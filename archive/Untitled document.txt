CRM Database Refactor – Discovery Questions & Migration Checklist
Purpose
This document contains all required questions, validations, risks, and migration checks before removing or restructuring fields in CRM 3.0 database collections.
Goal:
* Remove unused/redundant fields
* Avoid breaking CRM 1.0 legacy data
* Prevent frontend/backend runtime errors
* Prevent reporting/payment/traveler/history issues
* Ensure backward compatibility during deployment

IMPORTANT QUESTIONS BEFORE CHANGING BOOKINGS
________________


1. Is Existing UI Already Using segments[] Everywhere?
Questions:
* Are ALL booking pages already migrated to segments[]?
* Is any screen still reading:
   * travelDate
   * returnDate
   * flightFrom
   * flightTo
   * tripType
Check:
* lead details page
* reports page
* edit booking page
* booking card UI
* calendar
* exports
* PDF generation
* ticketing
* operations dashboard
* WhatsApp templates
* admin analytics
________________


2. Are APIs Backward Compatible?
Questions:
* Do APIs still return old fields?
* Does frontend expect old fields?
* Does any mobile/webhook integration expect old schema?
Need to verify:
* GET booking
* CREATE booking
* UPDATE booking
* CONVERT lead to booking
* duplicate booking flow
* export APIs
* report APIs
________________


3. Will Old CRM 1.0 Data Break?
Questions:
* Do old records contain ONLY old fields and no segments?
* What happens when frontend opens old booking?
Need fallback logic:
if (!segments?.length) {
   use legacy fields
}


Question:
Will migration script convert ALL old records?
Or:
Will system support both schemas temporarily?
________________


4. Can Reports Break?
Questions:
* Are reports aggregating:
   * amount
   * pricePerTicket
   * tripType
   * travelDate
from booking collection directly?
Need to inspect:
* dashboard stats
* monthly sales
* revenue reports
* ticket reports
* travel calendar
* finance exports
________________


5. Is amount Truly Redundant?
Current understanding:
estimatedCost.totalEstimatedAmount


already stores amount.
Questions:
* Is amount used anywhere for:
   * quick filters?
   * sorting?
   * dashboard totals?
   * commissions?
   * old reports?
If removed:
* what becomes source of truth?
* estimated total?
* actual total?
* payment total?
________________


6. Is pricePerTicket Used Anywhere?
Questions:
* Does any:
   * markup calculation
   * vendor costing
   * invoice logic
   * ticketing flow
   * Excel export
still use it?
________________


7. Should includesFlight Be Derived Instead?
Possible replacement:

Question:
Do we still need explicit boolean fields?

8. Should includesAdditionalServices Be Removed?

MIGRATION STRATEGY QUESTIONS
________________


1. Big Bang Migration or Gradual?
Options:
Option A – Safe Gradual Migration (Recommended)
Phase 1:
* Add new schema
* Keep old fields
* Dual write
Phase 2:
* Migrate old data
Phase 3:
* Switch frontend fully
Phase 4:
* Remove old fields
Option B – Immediate Cleanup
Higher risk:
* runtime crashes
* missing data
* reporting failures
Question:
Which approach will be used?
________________

FINAL QUESTIONS CODING AGENT MUST ANSWER BEFORE CHANGES
________________


Mandatory Checklist
Data
* How many legacy CRM 1.0 records exist?
* How many records already use segments?
* Any null/invalid old fields?
Backend
* Any APIs still dependent on removed fields?
* Any validators using removed fields?
* Any aggregation pipelines using removed fields?
Frontend
* Any UI still reading removed fields?
* Any forms still sending removed fields?
Reporting
* Any reports/export/PDFs using old fields?
Migration
* Is migration reversible?
* Is backup created?
* Is dry-run supported?
* Is rollback plan defined?
Deployment
* Is backend backward compatible?
* Will old frontend still work during deployment?
Performance
* Any indexes affected?
* Any queries becoming slower?
________________


Recommended Immediate Next Step
Before deleting anything:
1. Create compatibility layer
2. Introduce segments[]
3. Dual-write old + new schema temporarily
4. Run migration
5. Verify reports/UI/APIs
6. Remove old fields only after validation
This is especially important because:
* CRM 1.0 legacy data exists
* CRM 3.0 is already live and working
* Empty fields are safer than premature deletions
* Runtime breakage risk is high in booking/payment systems
